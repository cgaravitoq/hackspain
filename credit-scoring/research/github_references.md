# Public implementation research: deterministic SME treasury health

Inspection date: **2026-09-19**. Owner: AGENT2, PHASE 1. Research only.

## Executive conclusion and scope

**No direct implementation matching the full requested treasury-health contract was found in the searches below.** This is a bounded search finding, not a claim that none exists. Four repositories were inspected at fixed revisions. They provide adjacent examples of SME cash-flow metrics, pure financial calculations, additive scorecards, and configurable policies. None supplies the required combination of a deterministic 0–100 score, six-calendar-month comparisons, persistence-gated adjustments bounded by ±10, separate confidence, and reconciled record-level evidence.

Use patterns, not repository code or packages. Two examples have verified MIT licenses; two have no identified license and must not be copied without permission. ML/WOE/logistic scorecards are explicitly **not** the scoring method for this project, even where inference from a fitted model is deterministic.

The recommendations below are compatible with a small Python-only, offline CLI. They do not establish empirical thresholds, calibrated credit-risk probabilities, lending suitability, or regulatory compliance. **Score trajectories are operational indicators, not validated credit-risk probabilities.** Confidence describes observation reliability, not default probability or the probability that a score is correct.

Local context read: `README.md`, `agents/AGENT2_research.md`, and the complete AGENT3, AGENT4, and AGENT5 instructions. This research does not replace AGENT1's schema/classification audit, inspect banking records, or authorize assumptions about source field names. AGENT3 must wait for both this report and AGENT1's completed audit, and escalate unresolved essential inputs.

### R1 — SME cash-flow underwriting: closest domain, not a direct fit

Inspected files:

- [credit_underwriting.py](https://github.com/jaysavani713/sme-credit-underwriting/blob/f629e52a78eee2c7971e22e9383db23d3cd4d82b/credit_underwriting.py)
- [README.md](https://github.com/jaysavani713/sme-credit-underwriting/blob/f629e52a78eee2c7971e22e9383db23d3cd4d82b/README.md)

**Actual implementation.** `process_underwriting` reads one transaction CSV, computes net operating income and debt-service coverage, separates debt payments using description patterns, counts insufficient-funds events, assigns A–D grades from DSCR cutoffs, and forces grade D when NSF count exceeds two. `calculate_liquidity_and_volatility` computes cash days and monthly revenue variation. `macro_stress_test` applies a hypothetical interest-rate shock to estimated floating debt. README describes the included transaction data as synthetic; that is an author statement, not a dataset verification performed here.

**What it does well.** Small named functions expose the arithmetic. Operating payments and debt service are distinguished rather than indiscriminately netted. Metric outputs and downgrade notes make the broad decision path visible. The stress-test principal proxy is disclosed instead of hidden.

**Patterns to adapt, independently.** Separate transaction classification, metric calculation, and score mapping. Retain numerator, denominator, excluded-category totals, and rule identifiers so a metric can be checked. This decomposition fits AGENT3/4 without adopting DSCR as a new required component. Only use financial coverage definitions supported by the audit.

**What to avoid.** The source counts all credits as revenue, so financing receipts and internal transfers could inflate health. There is no currency separation or historical scoring cutoff in the inspected pipeline. Description regexes are dataset-specific, not a validated classifier. Liquidity and main-pipeline debt classifiers are not identical: for example, `LINE OF CREDIT` is recognized in the main floating-debt mask but not the liquidity exclusion regex. Reimplement one audited classification policy, not two drifting copies.

Monthly revenue uses `resample('ME').sum()` without an observation-preserving missingness policy: empty intermediate buckets can become zero, which is incompatible with our missing-month rule. A mean of transaction-row running balances is not necessarily a time-weighted daily balance. Zero debt or burn can produce `np.inf`; zero/absent revenue can produce CV zero, masking insufficient data. Thresholds and downgrades are hard-coded, grades are not 0–100, outputs are rounded before serialization, and default `json.dumps` does not enforce finite JSON. No six-month trajectory, independent persistence calculation, separate confidence object, or source-record lineage is supplied.

**Compatibility / license decision.** Adjacent domain example only. Imports pandas/NumPy; neither is justified merely to reuse its simple formulas. No copying from this unlicensed repository. No adoption of its A–D thresholds, lending conclusions, or stress assumptions.

### R2 — FinanceToolkit: pure financial formulas and decomposed criteria

Inspected files:

- [liquidity_model.py](https://github.com/JerBouma/FinanceToolkit/blob/9fa19f9e97fee229dad4d65cf9c1448597af5df5/financetoolkit/ratios/liquidity_model.py)
- [piotroski_model.py](https://github.com/JerBouma/FinanceToolkit/blob/9fa19f9e97fee229dad4d65cf9c1448597af5df5/financetoolkit/models/piotroski_model.py)
- [test_liquidity_model.py](https://github.com/JerBouma/FinanceToolkit/blob/9fa19f9e97fee229dad4d65cf9c1448597af5df5/tests/ratios/test_liquidity_model.py)
- [pyproject.toml](https://github.com/JerBouma/FinanceToolkit/blob/9fa19f9e97fee229dad4d65cf9c1448597af5df5/pyproject.toml)
- [LICENSE.txt](https://github.com/JerBouma/FinanceToolkit/blob/9fa19f9e97fee229dad4d65cf9c1448597af5df5/LICENSE.txt)

**Actual implementation.** Liquidity functions accept financial inputs and return ratios or working capital without fetching data inside those functions. Examples include operating cash flow/current liabilities and operating cash flow/short-term debt. The Piotroski module calculates named boolean financial-statement criteria and adds nine criteria into a 0–9 score. Change criteria compare current data with `.shift(1, axis=1)` predecessors. Ratio tests pass small pandas Series into named functions and capture outputs.

**What it does well.** Explicit financial input names, documented formulas/units, reusable stateless arithmetic, separation of metric calculation from aggregate scoring, and small synthetic formula fixtures. Piotroski demonstrates directional criteria that can be inspected without a black-box prediction.

**Patterns to adapt.** AGENT3 can use scalar pure Python functions returning metric intermediates and a separately mapped component score. Document cash-flow coverage units and time periods as explicitly as the ratio functions. AGENT5 can use tiny, manually computable fixtures rather than relying only on large end-to-end outputs.

**What to avoid.** Financial-statement ratios are not interchangeable with bank-transaction metrics: liabilities, assets, and accruals cannot be invented from unrelated fields. The inspected liquidity functions divide directly without a project-specific denominator policy. Piotroski comparisons do not implement our explicit missingness contract; ordinary float NaN comparisons may become false criteria and hence zero points. Positional shifting does not establish adjacent calendar months if columns have gaps. Its fixed nine-criterion equal-point mapping is not our configurable four-component 0–100 score. It does not supply our trajectory/persistence/confidence contract.

**Compatibility / license decision.** Adjacent deterministic finance example, not a treasury-credit engine. Adapt the functional decomposition, not Piotroski's score or accounting assumptions. MIT permits reuse subject to notice obligations, but no source copying is proposed. Installing the full package would pull pandas, scikit-learn, requests, yfinance, openpyxl, and PyYAML according to the inspected manifest; unnecessary for the small offline CLI. This dependency observation is about the manifest, not a claim that the inspected ratio functions themselves call the network or train models.

### R3 — toad: inspectable additive scorecard structure, not our scoring method

Inspected files:

- [toad/scorecard.py](https://github.com/amphibian-dev/toad/blob/4317ecef972d68b82db15a17ed0c031cf10fdcca/toad/scorecard.py)
- [toad/scorecard_test.py](https://github.com/amphibian-dev/toad/blob/4317ecef972d68b82db15a17ed0c031cf10fdcca/toad/scorecard_test.py)
- [requirements.txt](https://github.com/amphibian-dev/toad/blob/4317ecef972d68b82db15a17ed0c031cf10fdcca/requirements.txt)
- [LICENSE](https://github.com/amphibian-dev/toad/blob/4317ecef972d68b82db15a17ed0c031cf10fdcca/LICENSE)

**Actual implementation.** `ScoreCard` instantiates logistic regression, can fit on WOE-transformed features, and generates point rules. It can also load an explicit card: `test_load` exercises a manually supplied bin-to-points mapping. `bin_to_score(..., return_sub=True)` sums per-feature point lookups and returns the component breakdown. `_check_rules` checks combiner/WOE bin compatibility; `_generate_testing_frame` generates threshold-adjacent examples. Export supports tabular/JSON/CSV representations. Other methods convert score and probability using odds scaling.

**What it does well.** Scoring rules and per-feature values are inspectable; loading rules is separable from fitting; boundary samples, rule-shape errors, unknown categories, and rule export/import receive targeted tests.

**Patterns to adapt.** Represent independently authored fixed thresholds as data; keep a single deterministic mapping function; return component contributions beside totals; test thresholds at, below, and above each boundary. Use explicit missing/unavailable states instead of an implicit bin. These patterns support AGENT3 and AGENT4 without fitting or importing toad.

**What to avoid.** Learned WOE, coefficients, logistic probabilities, PDO/odds scaling, median-based learned reasons, and PMML are outside scope. A deterministic prediction from a trained model is still model-dependent. `bin_to_score` defaults unknown groups to the minimum score, which would turn missingness into a health penalty here. `_format_rule` rounds exported scores to two decimal places by default; do not use rounded presentation mappings as authoritative reconciliation data. These subscores explain the base card, whereas our public `signals.contribution` must explain only the effective trajectory adjustment. `get_reason` is not record-level evidence lineage.

**Compatibility / license decision.** Adjacent scorecard-engineering example; neither the library nor its learning method is recommended. MIT notice obligations apply if copying were later authorized. Its NumPy/pandas/scikit-learn/SciPy ecosystem, native-extension activity, and optional PMML tooling add unnecessary complexity for this Python-only CLI.

- [tests/test_policy_engine.py](https://github.com/saubhagyapandey27/lending-lifecycle-platform/blob/3966296e0e046781d14ab1e8fedf512343ac65b7/tests/test_policy_engine.py)

**Actual implementation.** YAML declares a policy version, risk tiers, thresholds, knockout rule IDs, and reason descriptions. `PolicyEngine` uses `yaml.safe_load`, evaluates operators, returns triggered rules with actual values and thresholds, and carries the policy version in a dataclass result. Pydantic request fields express some numeric constraints. Tests check approval/referral/decline, a specific triggered rule, and exposure capping. The separate `LogisticPDScorecard` trains logistic regression on WOE inputs, emits default probabilities, and scales/rounds scores to 300–850.

**What it does well.** Business policy is visible outside Python; policy identifiers and reason codes survive evaluation; request contracts are separated from policy evaluation. The knockout test checks the triggering rule ID, not only the final decision. These are useful structural examples for configuration and evidence.

**Patterns to adapt, independently.** Keep versioned rule definitions separate from the engine; return structured reasons containing rule ID, observed metric, threshold, and outcome; validate contracts before scoring. Preserve the rule version in every exported report. These are concepts, not a recommendation to copy this unlicensed implementation or its applicant schema.

**What to avoid.** Safe YAML parsing is not semantic validation. The inspected loader does not validate threshold ordering, gaps/overlaps, finite numbers, unknown operators, or all required keys. Missing knockout fields are skipped, and numeric conversion exceptions are silently ignored. Tiers fall back to “Deep Subprime” when none matches, disguising out-of-domain input as a poor rating; tier intervals are integer-oriented and need explicit semantics for continuous values. Some behavior is duplicated: `score_cutoffs` is loaded but decisions use risk tiers and knockouts; `outcome` is present in YAML but triggered knockouts are hardwired to decline. Do not create configuration that appears adjustable but is unused.

The scorecard fills missing features with zero and independently rounds/clips totals and point breakdowns without an explicit reconciliation check. `PolicyDecisionResult.to_dict` also rounds values. Request defaults invent demographic/tenure values; none belongs in this SME treasury score. Do not inherit ML, lending approval/pricing, regulatory claims in comments/README, or the README's “tamper-proof”/reproducibility assertions. The audit persistence implementation was not inspected, so this report does not endorse those assertions.

**Compatibility / license decision.** Adjacent configuration/schema example, not a direct deterministic treasury score. No identified license grant: independent design only. FastAPI, SQLAlchemy, database drivers, XGBoost, dbt, and the larger platform dependency set are unsuitable additions for this CLI. Small standard-library validators can express our contract; adding Pydantic is not necessary just because this project uses it.

## RECOMMENDED PATTERNS

The following are **our own design recommendations**, informed by the named inspected references where applicable. They are not claims that the references already implement our contract. Audit-dependent choices must be resolved by AGENT3 with the coordinator, not guessed here. Each item includes its rationale and compatibility assessment.

### AGENT3 — Engine and configuration

1. **Validate a declarative configuration once, before loading scoring state.** Use actual safe YAML parsing with an explicitly selected, pinned parser dependency communicated to AGENT5; never treat YAML as JSON or execute expressions from it. Reject duplicate keys, unknown/misspelled settings, missing required fields, booleans where numbers are required, NaN/Infinity, negative weights, and all-zero weights. Choose and declare one normalization convention: for raw nonnegative weights, store `normalized_weight = weight / sum(weights)` once in fixed component order. Validate threshold arrays as strictly increasing with equally sized scores, bounded 0–100 and monotonic in the declared direction. Validate positive integer windows/persistence, nonnegative materiality/scale, cap in [0, 10], seasonal months in 1–12, tight positive numerical tolerance, policy enums, and `rule_version: v1.0.0`. Reject incompatible policy combinations rather than silently defaulting. **Rationale:** configuration mistakes must not become plausible-looking scores. **Reference:** R4's [YAML](https://github.com/saubhagyapandey27/lending-lifecycle-platform/blob/3966296e0e046781d14ab1e8fedf512343ac65b7/config/policy_rules.yaml) and loader motivate separation, while their missing semantic checks show the gap. **Compatibility:** standard Python validation plus one explicit YAML parser; no generic rule framework or copying needed.

2. **Separate I/O, normalization, metrics, component mapping, and aggregation.** Expose the engine APIs required by AGENT3; scoring should take validated observations, a validated config, and an explicit date, return a fresh result, and neither read the clock nor mutate inputs. Use a single audited classification function across every metric. Return each metric's numerator, denominator, units, eligibility, reason for absence, mapped score, and normalized weight. Use strings for company IDs and preserve original record locators before sorting/filtering. At the dataset boundary validate audited required tables/columns, parseable dates, finite amounts and their audited sign convention, identifier relationships, and currency presence/eligibility. Reject ambiguous critical mappings; record explicit row exclusions only where the audit authorizes them. Do not silently coerce malformed values into zeros. **Rationale:** one policy path prevents CLI/report drift and enables tiny deterministic tests. **References:** R1's named metric functions and R2's [liquidity functions](https://github.com/JerBouma/FinanceToolkit/blob/9fa19f9e97fee229dad4d65cf9c1448597af5df5/financetoolkit/ratios/liquidity_model.py). **Compatibility:** pure scalar Python suffices; no finance or ML package. Actual source-column mappings come only from the audit.

3. **Make component scoring monotonic and explainable.** Choose one configured mapping convention, such as piecewise-linear interpolation between finite ordered knots with explicit endpoint clamping. For higher-is-healthier metrics, knot scores must not decrease; reverse this for chargeback and fee/interest loads. Record the active segment and interpolation operands. Apply the identical mapping to base and comparison windows; compute weighted scores with fixed normalized weights and stable summation order. Validate dimensionally consistent numerator/denominator windows before scoring. **Rationale:** improving one observed metric should not worsen its component score, and threshold boundaries must have unique interpretations. **Reference:** R3's [explicit card and boundary tests](https://github.com/amphibian-dev/toad/blob/4317ecef972d68b82db15a17ed0c031cf10fdcca/toad/scorecard_test.py) inspire inspectable lookup/boundary tests, not interpolation or our thresholds. **Compatibility:** deterministic policy mapping, not learned WOE; knot values remain audit-informed v1 policy, not empirical default calibration.

4. **Represent missingness separately from amounts and confidence.** Build an explicit monthly observation structure: calendar label, completeness status, eligible record count, observed totals or `None`, and reasons. Do not convert a month without observations into zero; preserve genuinely observed zero totals. A zero denominator is a domain case requiring a stated policy, not Infinity or an invented perfect/poor score. Never automatically renormalize away unavailable components separately in recent/baseline windows: it changes the score being compared. Require the same valid positive-weight components for directional comparison; otherwise return `insufficient_data`. If a numeric base score needs a configured neutral fallback, label it as policy-imputed/insufficient, retain the unavailable metric as null, and never use that fallback to establish a trajectory. Escalate if the audit cannot support a defensible fallback. **Rationale:** absence of evidence is not measured deterioration or improvement. **References:** avoid R1's resampling/Infinity, R2's NaN-to-false criteria, and R3's minimum-score unknown default. **Compatibility:** satisfies finite public scores while making any authorized fallback explicit; no arbitrary fallback value is prescribed here.

5. **Use closed calendar windows and genuinely distinct persistence endpoints.** Default the scoring date from the latest valid audited transaction date, not wall time, and derive the last closed calendar month unless the audit proves another completion rule. For endpoint `t`, compare calendar months `[t-2, t-1, t]` with `[t-5, t-4, t-3]`. For the previous confirmation endpoint, independently compare `[t-3, t-2, t-1]` with `[t-6, t-5, t-4]`. Thus six usable months permit one comparison, while two consecutive endpoints normally require seven. More generally, recent-window length plus baseline-window length plus persistence count minus one gives the minimum contiguous span. Missing endpoints, stable/insufficient comparisons, reversals, or unresolved seasonal gates prevent confirmation. Record August/December flags before deciding deterioration; apply the explicit conservative policy, not an unvalidated seasonal correction. **Rationale:** positional shifts and the last six nonempty buckets can bridge gaps or fabricate persistence. **References:** R1 resampling and R2 positional shifts are cautions, not implementations of this rule. **Compatibility:** Python calendar/date arithmetic; overlapping comparisons are operational corroboration, not statistically independent evidence.

6. **Enforce currency and point-in-time eligibility before aggregation.** Exclude and count non-EUR and unknown currencies before any sum; do not infer FX conversions. Apply scoring-cutoff and closed-period eligibility consistently to metrics, confidence, and evidence. Exclude financing/internal transfers and handle reversals/duplicates using AGENT1's audited policy. Current debt/invoice states cannot reconstruct historical conditions without cutoff-safe history; platform registration is not company founding. Preserve exclusions as reason-coded metadata, not scoring evidence. **Rationale:** contaminated inputs can yield perfectly deterministic but invalid scores. **Reference:** R1's all-credit revenue aggregation illustrates the classification risk; no inspected reference establishes all these safeguards. **Compatibility:** our own required controls, Python-only, immutable source data, no new data assumptions.

7. **Keep confidence as an independent output.** State the horizon for `months_available`, `months_complete`, and `coverage_pct`, and the expected-month denominator, explicitly; do not silently shrink the denominator to observed months. Count only eligible cutoff-safe observations, make complete months a subset of available months, and retain coverage in [0, 100]. One defensible policy candidate is the fixed span required for current persistence evaluation, but the audit must settle completeness semantics. Use exactly `EUR_only`, `multi_excluded`, or `insufficient`, with a documented precedence when exclusion and insufficient data coexist. Never multiply, subtract, or otherwise adjust health scores using confidence. **Rationale:** evidence reliability and financial coverage are different concepts. **Reference:** our own design; none of R1–R4 provides the specified object. **Compatibility:** aligns with AGENT3/4; changing confidence metadata alone must not change base score or adjustment.

8. **Compute adjustment and signal reconciliation in one engine path.** Let `delta_i` be recent minus baseline normalized component-score points, `raw_i = adjustment_scale * normalized_weight_i * delta_i`, and `raw_total = sum(raw_i)`. Only confirmed improving/deteriorating trajectories can receive an adjustment. Gate first, cap the signed total by the configured cap (at most 10), then clip `base + capped_total` to [0, 100]. Define `effective = final - base`. When eligible and the raw total is nonzero, apply the same factor `effective / raw_total` to every raw contribution. If gated off or the total is zero, all effective contributions are zero; preserve raw terms in evidence. Define near-zero handling with the shared tight tolerance, and ensure trajectory materiality and adjustment eligibility use compatible rules. Omit unavailable directional signals rather than assigning fictitious zero changes; keep absence reasons in evidence. **Rationale:** public contributions must sum to the actual adjustment, including caps and score-bound clipping. **Reference:** R3 demonstrates additive breakdowns, but this adjustment-only proportional reconciliation is our own design. **Compatibility:** no ML; AGENT4 verifies rather than recalculates policy. Synthetic checks with confirmed direction and cap 10: base 98/raw +8 gives effective +2; base 3/raw −8 gives −3; raw ±20 away from boundaries is limited to ±10. Test a lower configured cap separately.

### AGENT4 — Traceability and strict reconciliation

9. **Build a compact evidence graph without a graph framework.** Preserve locators `(relative source file/table, original record ID or reproducible original row position)`; union/deduplicate the eligible records actually used across base, trajectory, and every persistence endpoint. Count and date-range that union, not all imported rows and not only the latest six months. Retain ordered monthly observations, component intermediates, mapping segments, applied weights, comparison endpoints, gates, raw terms, scaling, effective contributions, and limitations in the companion evidence structure. Link by company ID and scoring date; avoid raw descriptions, account details, or unnecessary banking fields. **Rationale:** a reason label or hash alone cannot reproduce arithmetic. **References:** R4's [triggered-rule structure](https://github.com/saubhagyapandey27/lending-lifecycle-platform/blob/3966296e0e046781d14ab1e8fedf512343ac65b7/src/policy/policy_engine.py) and R3's subscores are starting concepts, not complete lineage. **Compatibility:** ordinary Python dictionaries/records and immutable inputs; preserve AGENT4's exact public report shape and put details in the sidecar.

10. **Validate, never silently repair, engine results.** Raise `ReconciliationError` for nonfinite arithmetic or mismatch between contribution sum, adjustment, and `final - base`; check configured cap and the absolute ±10 bound. Unconfirmed/stable/insufficient cases must have zero adjustment and zero effective contributions. Validate score/coverage bounds, integer month counts, enums, rule version, ISO dates, exact report keys, consecutive ordered calendar windows, null missing months, cutoff-safe evidence, and complete evidence metadata. Use one configured tight absolute tolerance, not a permissive default relative tolerance. Preserve calculation precision through serialization; round only terminal display. **Rationale:** recomputing or rounding a mismatch away conceals an upstream defect. **References:** avoid R1/R3/R4 early rounding; R4's schema separation is useful but insufficient. **Compatibility:** deterministic pure Python validation; `json.dumps(..., allow_nan=False)` rejects nonstandard numeric JSON and `None` becomes `null`.

11. **Version the rules and retain reproducibility metadata.** Carry `v1.0.0` in every public report. In the evidence sidecar, retain the effective configuration or a canonical configuration digest with a retrievable config, engine revision when available, source-file content digests, source mappings/assumptions, and effective cutoff. Require a deliberate version change for policy changes; a fixed version string alone does not prove identical rules. Keep run-time timestamps out of semantic score results. A digest detects content changes when checked against a trusted reference; it does not prove authenticity or make files tamper-proof. **Rationale:** unchanged input/config/date should explain an identical score later without retaining sensitive duplicates. **Reference:** R4 carries policy versions; the stronger replay design is our recommendation, not a verified property of its audit storage. **Compatibility:** standard-library hashing/serialization, no database or external service required.

### AGENT5 — CLI, exports, and invariant tests

12. **Validate boundaries and publish one complete deterministic batch.** Resolve config relative to the entrypoint; parse strict dates and preserve string IDs, including leading zeros. Load/classify through AGENT3, build reports through AGENT4, and print a runtime `DATA AUDIT SUMMARY` without sensitive rows. Unknown IDs, critical schema drift, missing dependencies, and reconciliation failures must exit nonzero. Sort companies lexically as strings, periods chronologically, components by configured order, and evidence by stable locators; use stable reduction order as well as stable serialization. Write UTF-8 strict JSON and standard-library CSV with arrays/objects encoded as JSON cells. Validate the full batch before final publication and stage outputs so partial files cannot masquerade as a complete run; do not overwrite unrelated files without approval. Date filenames from the effective cutoff. **Rationale:** nondeterministic ordering, partial artifacts, or stale summaries defeat reproducibility. **References:** R4 demonstrates boundary schemas; R3 export demonstrates separate representations, but our batch/ordering guarantees are original recommendations. **Compatibility:** `argparse`, `pathlib`, `json`, `csv`, and engine/traceability APIs; no web framework or duplicate financial logic.

13. **Test mechanisms and invariants offline, then perform the mandated real-data validation.** Use small hand-calculable fixtures and the existing Python test setup, or standard-library tests if none is present. Do not install the reference repositories. Cover:

    - Invalid weights, thresholds, duplicate/unknown config keys, boolean numerics, nonfinite values, bad versions, invalid cap/window/persistence settings, and every threshold boundary. Improving a metric in its declared direction cannot reduce its mapped score.
    - Missing month versus genuinely observed zero, zero denominator, missing component, authorized fallback, no eligible EUR data, mixed/unknown currencies, and exclusion before aggregation. Adding excluded-currency records may change confidence/limitations, but not EUR arithmetic.
    - Fewer than six usable months; exactly six with a directional trajectory but unconfirmed persistence; seven with two independently recomputed matching endpoints; gaps/reversals/stable endpoints; August/December flags and conservative gating; leap years/year transitions; partial current month.
    - Explicit historical cutoff with future transactions and current snapshot fields that would otherwise alter a metric; assert the records/intermediates excluded, not only the final score. Hold the cutoff fixed when testing future-data exclusion because the default cutoff is dataset-derived.
    - Positive/negative caps, both score boundaries, mixed-sign contributions, exact/near-zero raw totals, gated-off signals, and independently tampered contributions/final totals. Reconciliation failures must raise and propagate, not be caught as successful reports.
    - Confidence-only metadata changes leave scores/adjustments unchanged. Input records remain unchanged after scoring; tests use read-only source fixtures. Evidence union deduplicates reused records across persistence windows; empty evidence has count zero, empty range, and a limitation.
    - Repeated runs with identical input/config/cutoff, stable input-order handling, strict JSON round trips without NaN/Infinity, CSV/JSON company and score parity, valid leading-zero IDs, invalid dates, unknown IDs, alternate working directory, and no apparently complete outputs after a failing batch.

    **Rationale:** numeric snapshots alone can pass through the wrong mechanism. **References:** R2's [tiny ratio fixtures](https://github.com/JerBouma/FinanceToolkit/blob/9fa19f9e97fee229dad4d65cf9c1448597af5df5/tests/ratios/test_liquidity_model.py), R3 boundary/unknown-rule tests, and R4's [rule-ID assertion](https://github.com/saubhagyapandey27/lending-lifecycle-platform/blob/3966296e0e046781d14ab1e8fedf512343ac65b7/tests/test_policy_engine.py) motivate targeted tests; the complete invariant matrix is ours. **Compatibility:** tests never reach the network. AGENT5 must additionally execute its required real-data all-company run and separate filtered/historical runs, inspect actual artifacts, and report commands, counts, dates, exit statuses, and limitations. Synthetic success cannot substitute for those runs. Do not start that phase until AGENT3 and AGENT4 have completed successfully.

These patterns deliberately produce a deterministic operational treasury-health indicator, not a trained model, validated lending decision, calibrated default probability, or financial advice. None authorizes changes to immutable input banking data.
